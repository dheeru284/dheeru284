# Database Design

PostgreSQL 16 with the `vector` extension (pgvector). Schema is managed only by
Alembic (`backend/alembic/versions`). The SQLAlchemy models in
`backend/app/models` are the code-side mirror of this document.

## 1. Conventions

- Primary keys: `UUID` (generated in the application, v4), except
  `audit_events.seq` (`BIGINT GENERATED ALWAYS AS IDENTITY`).
- Timestamps: `TIMESTAMPTZ`, stored in UTC. `created_at` on every table, with
  server default `now()`. `updated_at` only on mutable tables.
- Enumerations: `VARCHAR(n)` plus a named `CHECK` constraint (`ck_<table>_<column>`).
  Values are defined once, in `app/domain/enums.py`.
- Flexible structured data: `JSONB`, only where the shape is versioned
  elsewhere (AI inputs/outputs, ranking components, critic checks, audit payloads).
- Foreign keys: `ON DELETE RESTRICT` by default. Pipeline data is never
  cascade-deleted; it is part of the record.
- Naming: constraints follow a fixed convention (`pk_`, `fk_`, `uq_`, `ix_`, `ck_`)
  set in `app/db/base.py`, so autogenerated migrations are deterministic.

## 2. Entity-relationship overview

```
users ─┬─< submissions >─── entities (speaker, optional)
       │        │
       │        └─< claims >─── entities (speaker, optional)
       │              │
       │              ├─< retrieval_results >── source_chunks >── sources >── publishers
       │              │
       │              ├─< evidence >───────────┘ (source_id, chunk_id)
       │              │      └─< evidence_rankings
       │              │
       │              ├─< assessments ─< assessment_citations >── evidence
       │              │        ├─< critiques
       │              │        └─< review_tasks ─── review_decisions (1:1) ── users
       │              │
       │              └─< pipeline_jobs
       │
ai_runs  (referenced by claims, evidence, assessments, critiques; links to pipeline_jobs)
audit_events  (references any entity by type + id; no FKs, so it outlives nothing)
```

### 3.18 `audit_events`
Append-only, hash-chained.

| Column | Type | Notes |
|---|---|---|
| seq | bigint identity PK | total order |
| id | uuid unique not null | external reference |
| occurred_at | timestamptz not null | set by the application (it is part of the hash) |
| actor_type | varchar(10) not null | `USER`, `AGENT`, `SYSTEM` |
| actor_id | varchar(200) not null | user UUID, agent name, or `system:<component>` |
| action | varchar(100) not null | dotted verb, e.g. `claim.created`, `review.decided` |
| entity_type | varchar(50) not null | |
| entity_id | varchar(100) not null | |
| payload | jsonb not null | |
| prev_hash | char(64) not null | `"0"*64` for the first event |
| hash | char(64) unique not null | `sha256(prev_hash ‖ canonical_json(event fields))` |

Protection: trigger `audit_events_no_mutation` raises on `UPDATE`/`DELETE`;
`TRUNCATE` is blocked by a statement trigger. Appends take
`pg_advisory_xact_lock(<audit lock key>)` so the chain is linear under concurrency.

## 4. Claim status machine

| From | Allowed next statuses | Notes |
|---|---|---|
| `EXTRACTED` | `RETRIEVING`, `ASSESSING`, `FAILED` | `ASSESSING` directly for OPINION / PREDICTION / SATIRE |
| `RETRIEVING` | `EVIDENCE_READY`, `FAILED` | |
| `EVIDENCE_READY` | `ASSESSING`, `RETRIEVING`, `FAILED` | `RETRIEVING`: analyst re-runs retrieval |
| `ASSESSING` | `CRITIQUING`, `FAILED` | |
| `CRITIQUING` | `ASSESSING`, `NEEDS_REVIEW`, `FAILED` | `ASSESSING` is the bounded REVISE loop |
| `NEEDS_REVIEW` | `IN_REVIEW` | a reviewer claims the task |
| `IN_REVIEW` | `APPROVED`, `REJECTED`, `EVIDENCE_READY`, `NEEDS_REVIEW` | `EVIDENCE_READY` = REQUEST_MORE_EVIDENCE; `NEEDS_REVIEW` = task released |
| `FAILED` | `NEEDS_REVIEW` | stage failures always go to a human (`STAGE_FAILURE`) |
| `APPROVED`, `REJECTED` | — | terminal; reachable only from `IN_REVIEW` |

Allowed transitions live in `app/domain/state.py` and are unit-tested; services
refuse any transition not in the table.

## 5. Data retention and privacy

- No table stores data about private individuals beyond platform users.
- `sources.content_text` holds public documents only. Ingest is refused for
  content flagged as containing personal data of private persons (Phase 1 checklist).
- Rows are never hard-deleted in M1. Retraction is modeled as status changes
  plus audit events.

## 6. Migration policy

- One Alembic revision per logical change; autogenerate, then hand-review.
- Every migration has a working `downgrade()`.
- CI runs `upgrade head → downgrade base → upgrade head` on a fresh database.
- The `vector` extension is created in the first migration (`CREATE EXTENSION IF NOT EXISTS vector`).
